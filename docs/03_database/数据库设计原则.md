# 数据库设计原则

当前先以 PostgreSQL 为目标数据库进行设计。

## 分库存储

整体架构采用分库存储，而不是所有来源和数仓混在一个数据库中。

建议数据库职责：

```text
飞书录入数据库
  承接飞书多维表格录入、校验、回写、分发和流程状态。

抓取/采集数据库
  承接影刀抓取、Python 抓取、平台页面或导出数据处理。

数据仓库数据库
  承接各来源已处理数据，供 dbt 分层建模和分析使用。
```

原则：

```text
来源业务库负责流程闭环。
数据仓库库负责统一口径和分析建模。
dbt 只管理数据仓库库及其下游模型。
```

跨库入仓采用数据工程任务处理，优先使用：

```text
updated_at 增量抽取 + checkpoint + 目标表 upsert
```

## 建议逻辑层

```text
ods
  保存飞书/API/平台导出的原始或准原始数据。

biz
  保存经过校验、标准化后的业务过程数据和主数据。

flow
  保存跨环节流转任务、状态、目标和异常。

sync
  保存外部系统同步批次、记录映射、回写状态。
```

## 每个飞书环节建议对应

```text
ods.feishu_bitable_record_raw
biz_xxx
flow_xxx_task
sync_feishu_record_mapping
```

正式设计中，飞书 ODS 建议优先使用通用当前态表：

```text
ods.feishu_bitable_record_raw
```

不建议每读取一次就新增一条 ODS 原始记录。更推荐：

```text
一条飞书记录 = 一个稳定 ods_id
重复同步 = update raw_payload
```

如果某个高风险环节确实需要审计历史，再单独增加历史表或归档表。

## 重要原则

- 数据库生成长期主键。
- 飞书 record_id 只作为外部系统定位键。
- 业务实体主键和录入流水主键分开。
- 原始数据保留策略可以按表分级，不必所有 raw 永久保存。
- 所有关键业务表、标准表、任务表都必须有 `created_at` 和 `updated_at`。
- `updated_at` 必须在业务字段、状态字段、同步字段变化时刷新。
- 跨库同步和入仓任务默认按 `updated_at` 做增量。

## 时间字段规范

所有正式表建议统一包含不带时区的时间字段。
业务约定：所有时间值按北京时间理解和存储。

```sql
created_at timestamp not null default (now() at time zone 'Asia/Shanghai'),
updated_at timestamp not null default (now() at time zone 'Asia/Shanghai')
```

字段含义：

```text
created_at
  当前记录首次进入当前表的时间。

updated_at
  当前记录最近一次被业务流程或同步程序更新的时间。
```

增量入仓建议：

```sql
where updated_at >= :last_success_sync_at - interval '5 minutes'
```

使用回拨窗口后，目标仓库表必须按来源唯一键 upsert，避免重复入仓。

来源唯一键建议：

```text
source_system + source_table + source_id
```

如果存在多来源库，则增加：

```text
source_database
```
## 未来配置化元数据表

POC 阶段先按具体业务表落地，不急于把所有环节都抽象成配置中心。

当 1-2 条飞书录入链路稳定后，可以逐步沉淀以下通用元数据表：

```text
sys_process
  业务环节定义，例如产品开发、货源处理、图片处理、上架资料。

sys_process_field
  每个业务环节的字段定义，包括字段编码、显示名、类型、是否必填。

sys_field_mapping
  上下游环节之间的字段映射关系。

ops.task_run_log
  每次任务运行的批次、方向、状态、成功数量、失败数量和错误信息。当前日志模块已用 `ops.task_run_log` 替代早期设想中的 `sync_log`。

flow.feishu_distribution_task
  下游分发任务。用于解耦“业务处理完成”和“写入下游飞书表”。当前飞书 POC 已落地该表。
```

这些表的作用是把字段模板、校验规则、映射规则和同步审计从代码里逐步抽出来。

当前阶段不要过早引入完整工作流引擎，优先保证：

- 单个飞书表可以稳定读取、校验、入库、回写。
- 数据库里能追踪飞书记录和业务记录的关系。
- 同步失败可以定位原因并重试。
- 字段映射先配置化，流程配置后续再抽象。

## 同步与分发设计原则

飞书 API 写入和主业务入库要解耦。

建议原则：

- 主业务数据入库成功后，即使飞书回写失败，也不应回滚主数据。
- 飞书回写失败应记录错误，允许重试。
- 当需要把数据写入下游飞书表时，再引入分发任务表。
- POC 阶段可以直接回写原记录，不必立即建设完整分发任务系统。

一句话：

```text
先保证入库可信，再保证回写可重试，最后再做跨环节分发。
```
