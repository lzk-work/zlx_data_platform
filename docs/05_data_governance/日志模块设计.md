# 日志模块设计

## 1. 模块定位

日志模块是数据中台的横向能力，不属于某一个业务中心，也不只服务飞书录入。

它负责回答：

```text
哪一次任务运行了？
处理了哪些数据？
成功多少？失败多少？
失败原因是什么？
能不能重试？
重试到第几次？
这条业务数据在哪个环节出过问题？
```

核心原则：

```text
业务表保存业务事实，日志表保存系统运行过程。
```

产品、SKU、订单、库存等业务表不应混入大量同步日志、回写日志、异常堆栈和重试信息。日志、任务、checkpoint、错误明细应单独放在 `ops` 或各来源库的 `sync/flow` schema 中。

## 2. 日志分层

当前建议先分 5 类日志。

```text
1. task_run_log
   任务运行日志。记录一次任务从开始到结束的整体情况。

2. record_process_log
   单条记录处理日志。记录某条来源数据在某次任务中的处理结果。

3. validation_error_log
   校验错误日志。记录字段缺失、类型错误、枚举错误、唯一性冲突等业务校验问题。

4. external_api_log
   外部 API 调用日志。记录飞书、平台 API、OSS、其他服务的请求结果。

5. etl_checkpoint
   增量同步 checkpoint。记录来源表同步到哪里。
```

后续如果系统复杂，再增加告警表、任务配置表、日志归档表。

## 3. 日志与业务表边界

### 业务表应该保留

业务表只保留和业务事实有关的字段，以及少量必要审计字段：

```text
created_at
updated_at
created_by
updated_by
source_system
source_id
```

例如产品表可以知道这条产品来自 `manual`、`feishu`、`platform_export`，但不保存飞书 API 错误、回写失败详情、同步批次运行堆栈。

### 日志表应该保留

日志表保存运行过程：

```text
task_name
batch_id
source_system
source_table
target_table
status
started_at
finished_at
success_count
failed_count
error_code
error_message
retry_count
payload_snapshot
```

一句话：

```text
业务表回答“这是什么”。
日志表回答“系统怎么处理过它”。
```

## 4. Schema 建议

日志模块建议统一放在 `ops` schema。

```text
ops.task_run_log
ops.record_process_log
ops.validation_error_log
ops.external_api_log
ops.etl_checkpoint
```

如果某个来源库已经有 `sync`、`flow` schema，也可以这样分工：

```text
sync
  保存同步映射、checkpoint、批次状态。

flow
  保存分发任务、重试状态。

ops
  保存跨模块运行日志、错误日志、API 调用日志。
```

当前阶段为了简单，建议先统一落到 `ops`。等系统稳定后，再按职责拆细。

## 5. 状态枚举

### 任务状态

```text
pending
running
success
partial_success
failed
cancelled
skipped
```

### 记录处理状态

```text
success
failed
skipped
retrying
```

### 错误类型

```text
validation_error
mapping_error
database_error
api_error
writeback_error
distribution_error
etl_error
unknown_error
```

### 重试判断

```text
is_retryable = true
  网络超时、API 限流、数据库临时连接失败、下游服务暂不可用。

is_retryable = false
  必填缺失、类型错误、枚举错误、唯一性冲突、权限配置错误。
```

## 6. 任务运行日志

`ops.task_run_log` 记录一次任务运行的整体情况。

适用任务：

```text
飞书节点同步
飞书回写任务
飞书分发任务
抓取任务
OSS 上传任务
来源库入仓任务
dbt 运行任务
临时批处理脚本
```

关键字段：

```text
id
batch_id
job_type
job_name
node_code
source_system
source_database
source_table
target_database
target_table
status
started_at
finished_at
duration_ms
scanned_count
success_count
failed_count
skipped_count
error_message
created_at
updated_at
```

使用方式：

```text
任务开始时 insert running。
任务结束时 update success/partial_success/failed。
任务失败时记录 error_message，但不推进 checkpoint。
```

## 7. 单条记录处理日志

`ops.record_process_log` 记录某条数据在某次任务中的处理结果。

适用场景：

```text
飞书某一行是否入库成功。
某个 SKU 是否被映射成功。
某条订单是否入仓成功。
某个图片是否上传 OSS 成功。
```

关键字段：

```text
id
batch_id
task_run_id
source_system
source_table
source_id
target_table
target_id
process_stage
status
error_type
error_message
is_retryable
retry_count
processed_at
```

注意：

```text
不是所有成功记录都必须长期保存明细日志。
POC 和早期阶段可以保存成功与失败。
数据量变大后，可以只长期保存失败记录，成功记录保留汇总。
```

## 8. 校验错误日志

`ops.validation_error_log` 记录字段级和规则级错误。

适用场景：

```text
必填字段为空。
数字字段无法转换。
枚举值不在允许范围。
URL 格式错误。
业务唯一键冲突。
上游引用不存在。
```

关键字段：

```text
id
batch_id
source_system
source_table
source_id
business_key
field_name
field_label
rule_code
rule_message
raw_value
severity
created_at
```

严重程度建议：

```text
error
  阻止入库或阻止流转。

warning
  允许入库，但需要业务后续补充或关注。

info
  系统提示，不影响处理。
```

## 9. 外部 API 日志

`ops.external_api_log` 记录外部系统调用结果。

适用外部系统：

```text
飞书 API
平台 API
OSS API
图片处理服务
AI 服务
其他内部服务
```

建议不要保存敏感请求头、密钥和完整隐私数据。

关键字段：

```text
id
batch_id
provider
api_name
request_method
request_url
request_id
status
http_status
error_code
error_message
duration_ms
retry_count
called_at
```

请求和响应内容建议：

```text
request_payload_sample
response_payload_sample
```

只保存脱敏后的摘要或截断样本，不保存真实密钥、cookie、token 和完整客户隐私数据。

## 10. Checkpoint

`ops.etl_checkpoint` 记录增量任务同步到哪里。

适用场景：

```text
飞书来源库 -> 数据仓库
抓取库 -> 数据仓库
平台导出库 -> 数据仓库
图片资产库 -> 数据仓库
```

关键字段：

```text
source_system
source_database
source_table
target_database
target_table
last_success_sync_at
last_success_batch_id
last_status
error_message
updated_at
```

运行原则：

```text
读取 checkpoint
  -> 按 updated_at 回拨窗口抽取数据
  -> 目标表 upsert
  -> 全部成功后推进 checkpoint
  -> 失败时记录错误，不推进 checkpoint
```

## 11. 与飞书节点的关系

飞书节点中的同步、回写、分发都应该写日志，但飞书不是日志模块的唯一来源。

示例：

```text
运行 product_intake_poc 节点
  -> ops.task_run_log 记录本次节点任务
  -> ops.record_process_log 记录每条飞书记录处理结果
  -> ops.validation_error_log 记录字段级校验失败
  -> ops.external_api_log 记录飞书读取和回写 API 调用
  -> ops.etl_checkpoint 记录节点或入仓 checkpoint
```

飞书表里的“同步状态、校验结果、错误信息”是给业务人员看的轻量结果；数据库日志是给系统排查、重试和审计看的完整记录。

## 12. 与 dbt 的关系

一般情况下，dbt 不负责写日志。

但 dbt 运行结果可以由调度器或外部脚本写入：

```text
ops.task_run_log
```

记录：

```text
dbt run 是否成功
dbt test 是否成功
运行模型数量
失败模型
失败原因
运行耗时
```

dbt 模型本身仍只负责数据仓库内的建模，不处理来源系统日志。

## 13. 保留策略

早期可以先多保留，方便排查。

建议策略：

```text
task_run_log
  长期保留。

record_process_log
  失败记录长期保留；成功记录可保留 30-90 天。

validation_error_log
  至少保留 180 天，用于分析常见数据质量问题。

external_api_log
  脱敏后保留 30-90 天。

etl_checkpoint
  长期保留当前态，同时可以归档历史变更。
```

## 14. 当前落地优先级

第一阶段先落地：

```text
1. ops.task_run_log
2. ops.record_process_log
3. ops.validation_error_log
4. ops.etl_checkpoint
```

`external_api_log` 可以先简化为任务错误信息，等真实 API 调用增多后再完整落表。

不要一开始建设复杂日志平台、告警平台或工作流引擎。当前重点是：

```text
出错可定位。
任务可重试。
数据可追踪。
入仓不漏数。
```
