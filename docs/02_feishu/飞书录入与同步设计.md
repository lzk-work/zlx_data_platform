# 飞书录入与同步设计

## 定位

```text
飞书多维表格 = 业务录入与协作界面
数据库 = 数据中台的事实存储、校验、流转与标准口径中心
API 同步程序 = 飞书与数据库之间的数据通道
```

多个飞书录入表之间的节点流转抽象，见：

```text
docs/02_feishu/飞书录入节点流转设计.md
```

## 最小闭环

```text
业务人员录入飞书
  ↓
API 拉取记录
  ↓
字段映射与校验
  ↓
写入数据库
  ↓
生成处理状态
  ↓
API 回写飞书原记录
```

## POC 结论

飞书录入 POC 已验证以下能力可行：

```text
飞书应用鉴权
  -> 按过滤条件读取多维表格记录
  -> 读取字段结构
  -> 字段映射
  -> 必填/类型等基础校验
  -> 写入 PostgreSQL
  -> 保存飞书原始数据
  -> 写入标准业务表
  -> 维护飞书记录与数据库记录映射
  -> 按 record_id 回写飞书系统字段
  -> 创建下游分发任务
```

POC 的职责是验证可行性，不作为最终表结构和长期存储策略的直接照搬。正式设计应吸收 POC 中验证通过的能力，同时修正 POC 阶段为了排查方便而采用的临时策略。

POC 验证得到的关键结论：

- 飞书 API 可以通过 `filter` 参数服务端过滤记录，不需要先全量拉取再本地过滤。
- 飞书回写必须按 `record_id` 定位具体行；不会无条件更新整张表。
- 飞书支持单行回写，也支持批量回写；批量回写仍必须逐条指定 `record_id`。
- 动态字段适合进入 JSON 存储，不必为每个类目字段都建物理列。
- `target: column` 的字段必须对应数据库标准表中的真实物理列。
- 系统字段回写需要注意飞书字段类型，例如文本字段应回写字符串。
- 飞书 API 通常只返回有值字段，空字段不必在 ODS 中主动补齐。
- 回写和分发应拆成两套配置：回写更新来源行，分发创建或更新下游目标表。

## 正式 ODS 策略

正式设计不建议继续使用“每读取一次就新增一条 ODS 快照”的 POC 策略。

多个飞书多维表长期运行时，如果一条飞书记录对应多个 ODS ID，会带来两个问题：

```text
1. ODS 数据量随同步次数膨胀。
2. biz/sync 外键可能引用旧快照，后续清理复杂。
```

正式策略改为：

```text
一条飞书多维表格记录 = 一个稳定 ods_id
```

唯一定位键：

```text
feishu_app_token + feishu_table_id + feishu_record_id
```

同步规则：

```text
第一次读取该飞书记录
  insert ODS，生成 ods_id

再次读取同一飞书记录
  update ODS 当前态 raw_payload
  ods_id 保持不变

biz 标准表
  始终通过同一个 ods_id 关联该飞书记录
```

ODS 在正式设计中定位为“飞书原始当前态表”，不是审计流水表。需要历史时再单独建设历史表或归档机制。

建议正式 ODS 通用表：

```text
ods.feishu_bitable_record_raw
```

建议字段：

```text
id
  ODS 主键，一个飞书 record 对应一个稳定 id。

source_system
  固定为 feishu，方便后续扩展其他来源。

table_code
  业务表编码，例如 product_intake。

feishu_app_token
  飞书多维表格 app_token。

feishu_table_id
  飞书 table_id。

feishu_record_id
  飞书 record_id，用于 API 回写和来源定位。

raw_payload
  飞书 API 当次返回的整行 JSON。

raw_hash
  raw_payload 归一化后的哈希，用于判断原始内容是否变化。

feishu_updated_at
  飞书记录最后更新时间，优先使用飞书系统更新时间。

first_seen_at
  第一次进入数据库时间。

last_seen_at
  最近一次读取到该记录的时间。

last_synced_at
  最近一次成功完成业务同步的时间。
```

建议约束：

```sql
unique (feishu_app_token, feishu_table_id, feishu_record_id)
```

## 增量同步策略

正式同步不应长期全量扫描所有已完成记录。

推荐同步条件：

```text
开发状态 = 已完成
并且
飞书最后更新时间 >= 上次成功同步时间
```

飞书多维表格建议增加或使用：

```text
开发状态
  判断记录是否进入中台处理范围。

最后更新时间
  优先使用飞书系统字段或自动字段，不建议人工填写。

同步状态
  中台回写，用于业务侧查看处理结果。

同步时间
  中台回写，记录最近一次成功同步时间。

中台录入ID
  中台回写，用于从飞书追踪到数据库记录。

校验状态 / 校验结果
  中台回写，用于提示业务人员修正数据。
```

正式同步应维护 checkpoint：

```text
sync.feishu_table_checkpoint
```

建议字段：

```text
table_code
feishu_app_token
feishu_table_id
last_success_sync_at
last_sync_batch_id
last_status
updated_at
```

运行逻辑：

```text
读取 checkpoint
  -> 生成 read_filter
  -> 读取飞书增量记录
  -> upsert ODS 当前态
  -> raw_hash 未变化时可跳过 biz 重写
  -> raw_hash 变化时重新映射、校验、入库
  -> 回写飞书系统字段
  -> 更新 checkpoint
```

当前 POC 已支持从 `node.yaml` 的 `tasks[].read_filter` 读取结构化过滤条件，并支持 `incremental`、`reconcile` 这类节点任务。过滤条件可以包含固定值和相对时间窗口，例如 `-30m`、`-3d`。

但当前 POC 还没有真正接入 checkpoint 表来生成 `last_success_sync_time`。也就是说：

```text
已实现：按节点任务 read_filter 读取飞书记录。
未实现：读取 checkpoint -> 自动生成 last_success_sync_time -> 成功后推进 checkpoint。
```

## Mapping 正式规范

`table_mapping.yaml` 不只是字段名映射，还要表达字段存储和类型规则。

正式推荐结构：

```yaml
fields:
  product_name:
    feishu_field: "产品名称"
    target: column
    db_table: biz.product_intake
    db_column: product_name
    required: true
    feishu_type: text
    db_type: text

  purchase_price:
    feishu_field: "采购价格"
    target: column
    db_table: biz.product_intake
    db_column: purchase_price
    required: false
    feishu_type: text
    db_type: numeric

  product_features:
    feishu_field: "产品特点"
    target: dynamic_attributes
    required: false
    feishu_type: text
    json_type: text
```

规则：

```text
target: column
  必须配置 db_column 和 db_type。
  必须对应数据库标准表真实物理列。
  不能退回 JSON 存储。

target: dynamic_attributes
  写入 dynamic_attributes JSON。
  不需要 db_column。
  建议配置 json_type，便于校验。

feishu_type
  用于和飞书字段结构校验，避免录入端字段类型被改坏。

db_type / json_type
  用于入库前转换和校验，避免飞书文本直接写入数据库数字字段。
```

## 回写设计

回写分为系统字段和业务字段。

正式建议独立配置 `writeback.yaml`，不要把回写规则长期混在录入 mapping 中。

系统字段：

```yaml
fields:
  db_intake_id:
    feishu_field: "中台录入ID"
    value_from: db_intake_id
    type: text
  validation_status:
    feishu_field: "校验状态"
    value_from: validation_status
    type: text
  validation_message:
    feishu_field: "校验结果"
    value_from: validation_message
    type: text
  sync_status:
    feishu_field: "同步状态"
    value_from: sync_status
    type: text
```

业务字段：

```yaml
fields:
  product_sku:
    feishu_field: "商品SKU"
    value_from: product_sku
    type: text
  variant_code:
    feishu_field: "变体码"
    value_from: variant_code
    type: text
```

原则：

```text
回写必须按 record_id 定位行。
主业务入库成功后，即使回写失败，也不回滚主业务数据。
回写失败应记录错误并允许重试。
POC 阶段可单行回写；正式阶段可批量回写提高效率。
```

## 分发设计

分发不是回写。它的职责是把已经进入数据库、已经校验通过的数据，投递到其他业务目标表或下游处理环节。

正式建议独立配置 `distribution.yaml`：

```yaml
source_table_code: product_intake

targets:
  - target_table_code: sourcing_task
    enabled: true
    execute_immediately: false
    action_type: create
    target:
      app_token: ""
      table_id: ""
    fields:
      product_name:
        feishu_field: "产品名称"
        value_from: column_fields.product_name
      source_url:
        feishu_field: "来源链接"
        value_from: column_fields.source_url
      product_features:
        feishu_field: "产品特点"
        value_from: dynamic_attributes.product_features
```

目标飞书表的 `app_token` 和 `table_id` 属于业务流转配置，应放在 `distribution.yaml`。`.env` 只保存自建应用凭证、数据库连接、本地配置路径等运行环境参数。

配置粒度按来源录入节点划分。每个飞书录入表都有自己的 `table_mapping.yaml`、`writeback.yaml` 和 `distribution.yaml`。同一个 `distribution.yaml` 中的多个 `targets`，只表示当前来源节点可以分发到多个下游目标表，不表示所有节点共用一份全局分发配置。

推荐先落库任务，再由分发执行器处理：

```text
业务表入库成功
  -> 创建 flow.feishu_distribution_task
  -> 分发执行器读取 pending 任务
  -> 调用目标飞书表 API 新增/更新记录
  -> 标记 success/failed
  -> failed 任务可重试
```

这样做的好处：

```text
主入库和下游分发解耦。
目标表失败不影响来源表入库。
失败原因、重试次数、目标 record_id 都能追踪。
正式阶段可以按不同下游目标扩展多个执行器。
```

## ID 设计

不依赖飞书行号。行号会因为删除、排序、筛选发生变化。

建议分工：

```text
feishu_record_id
  飞书系统生成，用于短期定位当前行和 API 回写。

db_intake_id
  数据库生成，用于长期追踪一次录入事件。

business_id
  数据库生成，用于长期标识业务实体，例如 product_id、sku_id、listing_id。

entry_no
  可选。仅当业务人员需要可读编号、跨部门沟通编号、单据号时再增加。
```

原则：

```text
飞书 record_id 解决“当前这行在哪里”。
数据库 ID 解决“这件事后来去哪了”。
飞书自增ID只解决“人怎么称呼这件事”。
```

## 飞书容量策略

飞书只保留当前工作数据，不承担长期历史存储。

建议：

- 飞书表只保留近几天或当前待处理内容。
- 入库成功并完成必要回写后，记录可标记为可清理。
- 历史、版本、分析和追踪全部以数据库为准。
- 数据库保留飞书来源标识，用于同步排查和短期回写。
