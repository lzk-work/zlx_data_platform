# 分库存储与增量入仓架构

## 定位

这份文档描述整体数据架构中的“数据工程 / ELT”部分。

核心结论：

```text
业务来源库负责接收、校验、处理和状态流转。
数据仓库库负责统一入仓、建模、分析和指标管理。
dbt 只管理数据仓库库内的数据。
```

飞书录入、影刀抓取、Python 抓取、平台导出等来源，不直接混在数据仓库里做业务流程处理。它们先进入各自来源库，处理到“可入仓状态”后，再由数据工程任务同步到数据仓库。

## 分库原则

建议按系统职责拆分数据库。

```text
feishu_intake_db
  飞书录入专用数据库。
  负责飞书读取、校验、标准业务入库、回写、分发、流程状态。

crawler_db
  抓取/采集专用数据库。
  负责影刀抓取、Python 抓取、平台页面采集、采集任务状态。

warehouse_db
  数据仓库专用数据库。
  负责接收各来源已处理数据，并由 dbt 做分层建模。
```

后续如果出现更多来源，可以继续按职责拆分：

```text
platform_export_db
  平台导出文件接收和标准化。

image_asset_db
  图片下载、OSS 上传、图片资产处理。
```

分库不是为了把系统做复杂，而是为了让不同职责互不污染：

```text
业务流程库
  关注录入、校验、任务状态、回写、重试。

数据仓库库
  关注统一口径、历史沉淀、分析建模、指标交付。
```

## 数据流向

推荐流向：

```text
飞书录入库
  -> 抽取已完成、已校验、已标准化数据
  -> 数据仓库 ODS/STG
  -> dbt 建模
  -> DWD/DIM/DWS/ADS

抓取库
  -> 抽取已完成、已清洗、已标准化数据
  -> 数据仓库 ODS/STG
  -> dbt 建模
  -> DWD/DIM/DWS/ADS
```

抽象成统一模式：

```text
source database
  -> ELT extract/load task
  -> warehouse raw/staging table
  -> dbt transform
  -> business models and reports
```

## 增量同步

所有来源库的关键标准表都必须带更新时间，用于增量入仓。

统一字段建议使用不带时区的 `timestamp`。
业务约定：所有时间值按北京时间理解和存储。

```sql
created_at timestamp not null default (now() at time zone 'Asia/Shanghai'),
updated_at timestamp not null default (now() at time zone 'Asia/Shanghai')
```

字段含义：

```text
created_at
  当前记录首次进入当前表的时间。

updated_at
  当前记录最近一次被业务流程、校验、同步程序更新的时间。
```

增量抽取条件：

```text
updated_at > last_success_sync_at
```

为避免边界时间漏数，建议使用小窗口回拨：

```sql
updated_at >= last_success_sync_at - interval '5 minutes'
```

因为有回拨窗口，数据仓库写入必须幂等：

```text
同一来源记录重复抽取时，使用唯一键 upsert，不重复插入。
```

## 来源表入仓条件

不是所有来源库数据都应进入数据仓库。

每个来源标准表都应有明确的“可入仓状态”。

飞书录入库示例：

```sql
where validation_status = '校验通过'
  and sync_status = '已入库'
  and updated_at >= :last_success_sync_at - interval '5 minutes'
```

抓取库示例：

```sql
where process_status = 'processed'
  and data_quality_status = 'passed'
  and updated_at >= :last_success_sync_at - interval '5 minutes'
```

原则：

```text
来源库可以保存处理中、失败、待修正数据。
数据仓库只接收已完成、已校验、可用于后续建模的数据。
```

## 数据仓库落表规范

数据仓库接收来源数据时，应保留来源标识。

建议字段：

```text
source_system
  来源系统，例如 feishu、yingdao、python_crawler、platform_export。

source_database
  来源数据库，例如 feishu_intake_db、crawler_db。

source_table
  来源表，例如 biz.product_intake。

source_id
  来源表主键，例如 db_intake_id、task_id、record_id。

source_updated_at
  来源记录 updated_at。

extracted_at
  当前数据进入数据仓库的时间。

etl_batch_id
  当前入仓批次 ID。
```

数据仓库唯一键建议：

```text
source_system + source_table + source_id
```

如果同一个来源表可能跨多个来源库或租户，则增加：

```text
source_database
```

## Checkpoint

每个入仓任务都应维护 checkpoint。当前日志模块 DDL 已按 `ops.etl_checkpoint` 落地草案。

建议表：

```text
ops.etl_checkpoint
```

建议字段：

```text
source_system
source_database
source_table
target_table
last_success_sync_at
last_success_batch_id
last_status
error_message
updated_at
```

运行逻辑：

```text
读取 checkpoint
  -> 按 updated_at 回拨窗口抽取来源数据
  -> 写入数据仓库 ODS/STG
  -> upsert 去重
  -> 成功后更新 checkpoint
  -> 失败时记录错误，不推进 checkpoint
```

## 同服务器不同数据库的影响

同一台 PostgreSQL 服务器上，不同数据库之间同步数据，早期通常不会成为瓶颈。

需要理解的点：

```text
同服务器降低网络成本。
但 CPU、磁盘 IO、WAL、连接数仍然共享。
PostgreSQL 跨数据库不像同库 schema 那样可以直接普通 join。
```

可选同步方式：

```text
Python ETL 程序
  简单、灵活，适合当前阶段。

postgres_fdw / dblink
  适合需要 SQL 方式跨库读取的场景。

逻辑复制
  适合更高频、更标准化的数据复制。
```

当前阶段推荐：

```text
Python 数据工程任务 + updated_at 增量 + warehouse upsert
```

## dbt 边界

dbt 只处理数据仓库库内的数据。

建议边界：

```text
dbt 不负责飞书 API。
dbt 不负责影刀抓取。
dbt 不负责业务流程回写。
dbt 不直接管理来源业务库。
dbt 从 warehouse_db 的 ODS/STG 层开始建模。
```

数据仓库内部分层：

```text
ods / stg
  来源数据入仓和轻度标准化。

dwd / dim
  明细事实和维度建模。

dws
  面向主题的汇总层。

ads
  面向报表、看板和业务应用的数据集市。
```

## 设计原则

```text
来源库负责把数据处理到可信。
数据仓库负责把可信数据变成统一口径。
所有标准表必须有 updated_at。
所有入仓任务必须支持增量和幂等 upsert。
checkpoint 成功后再推进。
dbt 只在数据仓库库内工作。
```
